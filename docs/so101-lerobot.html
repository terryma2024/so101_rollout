LeRobot 0.6.1 · SO-101 · Feetech STS3215

主臂动一下，从臂怎么跟上

这一页按信号经过的顺序，讲 LeRobot 控制这套 SO-101 的每一层：舵机、串口总线、校准换算、舵机内部的位置闭环、60 Hz 主循环、摄像头和 rerun。数字取自这台工作站上的校准文件、实测和 LeRobot 源码。

一句话概括：主臂是一个关掉扭矩的位置传感器，从臂是一个位置执行器。LeRobot 每 1/60 秒把主臂 6 个关节的角度读出来，换算后作为目标角度写给从臂。点下图中的部件查看说明。

第 1 层 · 执行器

STS3215：自带控制器的总线舵机

每个关节是一颗 Feetech STS3215。它不只是一个电机，里面包含直流电机、减速齿轮组、一个 12 位磁编码器，以及一块带 MCU 的控制板。电脑从不直接控制电流或电压，只读写这块控制板上的寄存器。

4096编码器每圈刻度（0–4095），约 0.088°/刻度
12.2–12.3 V本机实测供电（寄存器 62 读数 122–123，单位 0.1 V）
44–49 °C本机实测舵机温度（寄存器 63）
型号 777STS3215 在 Model_Number 寄存器里的编号

控制表：舵机的全部接口

每颗舵机内部有一张按地址排列的寄存器表。EEPROM 区断电保留，用来存 ID、波特率、限位、PID 参数这些配置；RAM 区断电清零，是运行时的命令和状态。带左侧色条的行是遥操作循环里实际用到的。

第 2 层 · 通信

一根线串起 6 颗舵机

6 颗舵机首尾相连，共用一根 TTL 半双工数据线，通过 CH340 USB 串口板接到电脑，波特率 1 Mbps。半双工的意思是同一时刻只能有一方发送：电脑发完命令，把线让出来，被点名的舵机再回答。总线上没有地址线，靠每个包里的 ID 字节区分舵机。

这也解释了之前遇到的"找不到舵机 6"：任何一个接头接触不良，那颗舵机就收不到命令、也不应答。LeRobot 连接时会逐个 ping 一遍，少一个就拒绝启动。

数据包构造器

选一种指令看它在线上的实际字节。校验和是 ID 到最后一个参数之和取反后的低 8 位。STS 系列多字节数值是低字节在前。

电脑 → 舵机
舵机 → 电脑

为什么用 SYNC READ / SYNC WRITE

逐个读 6 颗舵机要发 6 个请求、等 6 次应答。SYNC READ 只发一个广播包（ID=0xFE），列出要读的 ID，舵机按顺序依次应答。SYNC WRITE 一个包里带 6 组目标值，舵机不回包。

本机实测
0.88 ms一次 SYNC READ 6 个位置，中位数（p95 0.97 ms，300 次）
0.62 ms理论线上时间：62 字节 × 10 bit ÷ 1 Mbps

差值来自 USB 转串口的延迟和舵机应答前的等待（LeRobot 把 Return_Delay_Time 设为最小的 2 µs）。

第 3 层 · 坐标换算

校准：让两只手臂说同一种角度

两只手臂装配时舵机花键插的位置不一样，同一个姿态下读到的原始刻度也不一样。校准记录每个关节三个数，存在 calibration/robots/so_follower/my_follower.json 和 calibration/teleoperators/so_leader/my_leader.json：

homing_offset · 中位偏移

校准第一步你把手臂摆到中间姿态，LeRobot 读出当前刻度，算出 offset = 当前刻度 − 2047，写进舵机的 Homing_Offset 寄存器（地址 31）。此后舵机固件报告的 Present_Position = 实际刻度 − offset，中间姿态正好读 2047。

range_min / range_max · 活动范围

第二步你把每个关节转到两头，LeRobot 记下最小和最大刻度。它们也被写入舵机的 Min/Max_Position_Limit 寄存器，所以就算程序发了超范围的目标，舵机固件自己也会拒绝转过头。

换算公式（motors_bus.py 的 _normalize）：身体关节 角度 = (读数 − (min+max)/2) × 360 / 4095；夹爪 (读数 − min) / (max − min) × 100。从臂用自己的 min/max 做反向换算。注意角度 0° 是校准范围的中点，不一定是你校准时摆的那个中间姿态。
第 4 层 · 舵机内部

位置闭环在舵机里跑

LeRobot 只写 Goal_Position，不管电机怎么转过去。从臂每颗舵机的 MCU 以远高于 60 Hz 的频率比较目标和编码器读数，用 PID 算出驱动电机的力度。主臂扭矩关闭（Torque_Enable=0），电机不出力，只有编码器在工作，所以你能用手掰动。

LeRobot 连接从臂时写入 P=16, I=0, D=32（出厂 P=32）。P 小一点、D 大一点，动作偏软、不容易抖。代价是 I=0：如果关节受到持续外力（重力、夹住的东西），会留下一点稳态误差。

模拟（简化模型，仅示意）

琥珀线是主臂角度（每 1/60 秒更新一次的目标），青色线是从臂响应。调参数看跟随效果的变化。

–平均跟随误差（度）
–最大超调（度）
–稳态误差（静止时，度）
夹爪单独加了保护：Max_Torque_Limit=500（50%）、Protection_Current=250（50%）、Overload_Torque=25。夹爪长时间夹着东西顶住，电流超过保护值就会触发过载，Status 寄存器第 5 位置 1（数值 32），舵机自动卸力。之前从臂夹爪读到的 status 32 就是这个，断电重启清除；今天实测两只手臂 Status 都是 0。
第 5 层 · 软件

60 Hz 主循环

teleop.sh 运行的 teleop_viz.py 是 lerobot_teleoperate 的包装。连接完成后，它每轮做四件事，然后睡到 1/60 秒（16.7 ms）凑满一个周期：

while True:
    t0 = now()
    action = leader.get_action()        # SYNC READ 主臂 Present_Position → 换算成角度
    robot.send_action(action)           # 角度 → 从臂刻度 → SYNC WRITE Goal_Position
    obs = robot.get_observation()       # SYNC READ 从臂位置 + 两路摄像头最新帧
    log_visualization_data(obs, action) # 发往 Mac 上的 rerun（图像限速到约 20 Hz）
    precise_sleep(1/60 - (now() - t0))
点选第几轮。teleop_viz.py 让图像大约每 3 轮发一次。

串口读写耗时为本机实测或按字节数计算；摄像头取帧和 rerun 发送的耗时是估计值，随画面内容和网络变化。

动作就是角度

action 是一个 6 个键的字典，例如 {"shoulder_pan.pos": 12.3, …, "gripper.pos": 41.0}。主臂提供它，从臂执行它，录制时存下来，训练时模型学着输出它。

可选的安全限幅

max_relative_target 可以限制每轮最多移动多少。开启后 send_action 会先读一次从臂位置再裁剪目标，多花约 0.9 ms。当前配置没有开启。

第 6 层 · 感知

摄像头不拖慢控制

每个摄像头由 OpenCV 打开，LeRobot 为它开一个后台线程不停抓帧，只保留最新的一帧。主循环调用 async_read 时直接拿这一帧，不等待。所以摄像头只有 20 fps，手臂控制照样 60 Hz；代价是连续三轮可能拿到同一帧。

第 7 层 · 观察

rerun：从工作站推到 Mac

--display_data=true 时，主循环每轮把关节数值和摄像头图像用 rerun SDK 发出去。通过 SSH 运行时，arms.env 取 SSH_CONNECTION 的第一个字段作为查看器地址，即你 SSH 的那台电脑。

版本要求

LeRobot 0.6.1 把 SDK 锁在 0.33.x，但查看器必须 ≥ 0.34：0.33 的查看器加载 JPEG 静态图会卡死，0.34.0 修复。Mac 上运行 uvx --from rerun-sdk==0.40.0 rerun --bind 0.0.0.0。

反压

SDK 发送队列满了会阻塞调用方。查看器一卡，rr.log 就卡，主循环跟着停，从臂不再跟随。所以 teleop_viz.py 把图像限到摄像头实际帧率，两个摄像头的数据量从约 12 MB/s 降到约 4 MB/s；也因此不用网页版查看器。

第 8 层 · 学习

录制数据，再让模型替代主臂

录制（record.sh）用的是同一个循环，每轮多做一件事：把这一刻的观测和动作作为一帧存进 LeRobotDataset。关节数据写 parquet，图像编码成 mp4。训练好的策略模型接收同样格式的观测，输出同样格式的动作。
